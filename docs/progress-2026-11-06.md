# Development and local validation progress

Updated: 2026-11-06
Feature implementation commit: `1de9f4b` (`feat: add secure tracking and optional sqlite storage`)

## Outcome

The requested local development work is implemented and functionally verified.
This does **not** establish readiness for intense or production use: the SQLite
performance campaign failed the provisional p99-under-1-second diagnostic in
the full soak and full-history tests. The VPS and its storage/backup policy have
not been inspected or tested.

## Delivered and verified locally

- Optional `modernc.org/sqlite` backend, with volatile memory remaining the
  default; timestamped schema migration created/managed with the pinned Goose
  CLI and explicitly applied outside application startup.
- Bounded SQLite group commit (queue capacity 64, batches up to 32, 2 ms
  collection); API success follows durable transaction commit. Queue overload
  fails closed, and protected metrics expose queue and batch error counts.
- Atomic single-use claim/ACK, proof verification, expiration, bounded terminal
  tracking, SQLite WAL cleanup tracking, and shutdown drain are covered by local
  integration/regression tests. SIGTERM during an in-flight write passed three
  repetitions; two application processes sharing one test DB also passed the
  single-winner lifecycle test.
- Memory-store history scans were replaced by indexed deadline/terminal queues;
  the measured memory-store history regression improved substantially. PWA
  remains online-only, with no offline cache.
- Local functional/security/browser gates passed: `make all`, `make lint`,
  `make security`, `make migrations-check`, `make e2e` (4/4),
  `make e2e-sqlite` (4/4), `npm audit --audit-level=moderate`, both default and
  SQLite Compose configuration checks, JavaScript syntax checks, and a
  CGO-free Linux ARM64 build. The ARM64 binary was built, not executed on ARM64.

## Performance result and acceptance boundary

Full group-commit campaign evidence and methodology are in
[`benchmarks/2026-10-30-sqlite-baseline.md`](benchmarks/2026-10-30-sqlite-baseline.md).
It used synthetic data, a local rootless container capped at 0.5 CPU/128 MiB,
and a local rotating ext4 disk, with `/tmp` supplied as a bounded tmpfs after
identifying SQLite error 6410 (`SQLITE_IOERR_GETTEMPPATH`) in the earlier
read-only-container setup.

- 10 cycles/s for 120 seconds: 3,600/3,600 completed; median run p99 1,435 ms,
  so 0/3 met the provisional <1,000 ms criterion.
- 25 cycles/s with 9,510 tracked records: 750/750 completed; median run p99
  1,867 ms, so 0/3 met the criterion.
- 100 cycles/s with full history: 1,716/3,000 completed; the next offered-load
  step was skipped after failures.
- A separate short fresh-store 5 cycles/s run passed 3/3 (150/150, median p99
  894 ms); it is not evidence of a long-term, full-history, or VPS capacity.

The diagnostic threshold is not a product SLO. Do not claim SQLite is ready for
heavy load based on these results or translate them into VPS capacity. Do not
weaken `synchronous=FULL`, deletion, or checkpoint semantics to improve a score.

## Outstanding and explicitly not performed

- No deployment, VPS access, or remote host change was performed as part of
  implementation validation. The repository's push workflow runs CI only; the
  blue/green SQLite path has not been exercised on the VPS.
- The operator must verify exclusions for the complete DB/WAL/SHM directory in
  backups and snapshots before enabling durable payload storage. The application
  acknowledgement does not verify that policy. Physical sanitization of all
  historical copies is not guaranteed.
- PostgreSQL remains a future operator-selectable open-source backend; no
  PostgreSQL adapter is implemented.
