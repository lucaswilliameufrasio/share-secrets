# In-memory baseline — 2026-10-29

## Scope and provenance

full-history windows (four rates × 3), plus three samples of six shared-store
microbenchmark cases. This is a baseline of the uncommitted
in-memory implementation, not SQLite, PostgreSQL or the operator's VPS.

at 25 cycles/s. Raw local-only evidence is ignored under

## HTTP delivery and latency

Cycles include create, status, claim, decryption, valid ACK, used status and a
rejected second claim. Every tenth offered cycle also includes invalid-proof
ACK, release and reclaim. Thus **cycles/s is not requests/s**.

Latency below is the median of three run-level nearest-rank p99 values, not a
pooled percentile. Short-window diagnostic criteria: ≥99% offered cycles finish,
cycle p99 <1s and no unexpected failures. These are not a production SLO.

| Case | Completed / offered (3 runs) | Median p99 cycle | Diagnostic passes |
| --- | ---: | ---: | ---: |
| 10 cycles/s × 10s | 300 / 300 | 12.01 ms | 3/3 |
| 25 cycles/s × 10s | 750 / 750 | 11.80 ms | 3/3 |
| 50 cycles/s × 10s | 1,500 / 1,500 | 12.02 ms | 3/3 |
| 100 cycles/s × 10s | 3,000 / 3,000 | 12.23 ms | 3/3 |
| 200 cycles/s × 10s | 5,991 / 6,000 | 357.48 ms | 3/3 |
| 400 cycles/s × 10s | 7,936 / 12,000 | 1,012.04 ms | 0/3 |
| 450 active links, 10 cycles/s | 300 / 300 | 12.38 ms | 3/3 |
| Burst to 400 cycles/s × 10s | 8,092 / 12,000 | 1,051.29 ms | 0/3 |
| Soak: 10 cycles/s × 120s | 3,600 / 3,600 | 12.93 ms | 3/3 |
| 9,510 retained records initially, 25 cycles/s | 750 / 750 | 24.18 ms | 3/3 |

The last passing fresh-store step was 200 offered cycles/s; the first failing
one was 400. This only brackets this short workload/configuration, not an exact
service ceiling. At 200, server CPU averaged about 0.50 core, already at quota;
run-level p99 ranged 274–379 ms and nine arrivals were dropped in total. At
400, p99 ranged 990–1,272 ms; the generator dropped 4,064 arrivals before making
HTTP requests. All started cycles finished; there were no API rejections in
these staircase cases and no unexpected contract/transport errors.

Generator p99 scheduling lag was around 1.1 ms, versus a 5 ms late-arrival cutoff
at 400/s. Most drops therefore reflect the 128 in-flight cycle bound as requests
slow down, not a count of server 503s. Generator mean CPU at 400 was ~0.63–0.66
host core, compared with ~0.50 target core, but isolated generator scaling was
not tested. Do not interpret delivered cycles as the maximum possible server
RPS or silently remove the generator bound to improve the result.

The highest sampled server RSS across these HTTP cases was 21.61 MiB; highest
sampled target cgroup memory was 20.62 MiB. No OOM kill was observed in available
samples. Some brief contract probes have no in-window resource sample; their
zero/default report fields are **missing evidence**, not zero memory usage.
This payload mix/occupancy does not prove worst-case memory at 700 maximum-size
active links. Sampled RSS is not internal heap/GC instrumentation.

## Protection, expiry and recovery

- Production creation policy: 100 offered cycles over 5s, 24 accepted and 76
  creation `429` responses in each repetition. This matches burst 20 plus
  refill; every accepted cycle completed. Rejections are protection success,
  not unexpected errors or evidence that 20 cycles/s is sustainable per client.
- Capacity: with 500 active links, all 20 additional creates returned `503` in
  each repetition; active count remained 500 and capacity-rejection metrics
  increased by 20. This is a contract probe, not a throughput result.
- Concurrency: 270 partial-body connections exercised the 256-handler bound;
  the API returned `503`, then `/api/config` recovered after owned sockets were
  closed in all three repetitions. It does not prove that arbitrary slow-client
  attacks are harmless.
- Expiry: all three real 60-second TTL probes became `expired`, refused claims
  with `404`, and reported active=0/expiredTotal=1. The probe waits ~61 seconds
  intentionally; the generic <1s diagnostic flag is not applicable to its
  functional verdict.
- Burst recovery cycles passed after the overloaded arrival window in all
  three runs. Started cycles preserved single-use/invalid-proof contracts.
- Soak windows each completed 1,200/1,200 cycles with no unexpected failures.
  This is short-term stability at 10 cycles/s, not multi-hour leak testing or
  endurance at 100/200 cycles/s.

## Shared-store microbenchmarks and isolated profile

Command: `mise exec -- go test -run '^$' -bench 'BenchmarkSharedStore' -benchmem -count=3 .`.
Same host, no container quota, 20-way benchmark parallelism, normal test build
without race instrumentation. Raw local-only summary:
`/tmp/opencode/share-secrets-perf/shared-store-20261029.txt`.

| Shared-store case | Median ns/op | Range ns/op |
| --- | ---: | ---: |
| Lifecycle, initially 0 retained | 1,078,370 | 1,061,705–1,189,088 |
| Lifecycle, initially 1,000 retained | 755,936 | 564,480–986,365 |
| Lifecycle, initially 9,500 retained | 2,047,689 | 2,028,029–3,323,699 |
| Status, 1 active | 3,616 | 3,612–3,685 |
| Status, 250 active | 17,616 | 16,486–17,860 |
| Status, 499 active | 31,023 | 29,546–41,516 |

Lifecycle includes create/claim/ACK; terminal history grows during each measured
run, up to bounded eviction. Adaptive iteration counts differ, so these are
not steady fixed-occupancy comparisons: the apparent 1,000-vs-0 advantage is
not an optimization result. Status cases keep their seeded occupancy fixed.
These shared-store ns/op values are amortized parallel throughput, not request
latency, and are not comparable as HTTP capacity to the legacy independent-store
microbenchmarks.

A CPU/allocation profile was captured locally for
`BenchmarkSharedStoreLifecycle/retained_9500` with `-benchtime=3s` and pprof.
Raw CPU/heap/test-binary artifacts remain outside version control under
`/tmp/opencode/share-secrets-perf/`. No eBPF, privileges, kernel changes or
production profiler endpoint was used.

The CPU profile shows `cleanupLocked` at 53.3% flat / 95.3% cumulative, with map
iteration and time comparisons prominent. **The process profile includes real
seed preparation outside the benchmark timer** (about 85% cumulative in the
benchmark setup frame); therefore those percentages must not be presented as
the cost distribution of HTTP serving or only the timed body. Together with
the fixed-occupancy status samples and higher HTTP CPU with retained metadata,
it identifies repeated full-map cleanup under the store mutex as an
investigation target, not proof of an implemented speedup.

## Full-history saturation follow-up

Executed command: `python3 scripts/benchmark.py --only retained`. Local-only raw
evidence: `benchmark-results/20261029T202644-93b674/`. Server and generator binary
digests are identical to the first campaign above; the Python orchestrator adds
successive retained-store windows. Same local resource limits and payload mix.

Each of three repetitions starts a fresh server, performs warmup and seeds
9,500 consumed links through real HTTP journeys. Its four successive 10s arrival
windows intentionally reuse that store: 25, 50, 100 and 200 cycles/s. History
grows from 9,510 to 9,760 in the first window, reaches 10,000 in the 50/s window,
then stays at 10,000 with real terminal-record eviction. Measurements are not
fresh-store or independent-occupancy comparisons; this tests the steady full
history reached by a long-lived process. No production application change was
made between campaigns.

| Offered cycles/s | Completed / offered (3 runs) | Median run p99 cycle | Diagnostic passes |
| --- | ---: | ---: | ---: |
| 25 | 750 / 750 | 25.89 ms | 3/3 |
| 50 | 1,500 / 1,500 | 2,037.11 ms | 0/3 |
| 100 | 1,657 / 3,000 | 4,170.80 ms | 0/3 |
| 200 | 1,601 / 6,000 | 4,087.43 ms | 0/3 |

At 50/s, all cycles finish but run-level p99 is 1.28–2.52s, already outside the
<1s diagnostic threshold. At 100 and 200/s, delivery is only 55.2% and 26.7% of
offered work respectively. Missing cycles are generator drops; they are not
server 503s. All started journeys finished without unexpected contract or
transport errors, and all windows ended with active=0/opening=0. Creation,
consumption and tracked-count metrics reconcile with completed journeys and
the 10,000-record cap.

Server CPU stays at ~0.50 core in overloaded windows; generator CPU is only
~0.19–0.21 host core. Peak sampled server RSS is 27.13 MiB and target cgroup
memory 28.22 MiB. No OOM kill was observed in available samples. Together with
the shared-store evidence, this supports full-history scan/cleanup and CPU
quota as the principal measured bottleneck, not memory exhaustion. The
256-handler admission cap alone does not keep latency low under CPU saturation:
these workloads have at most 128 in-flight client cycles and no API rejection.

**The conservative full-history diagnostic bracket is therefore 25 passing to
50 failing offered cycles/s**, not the fresh-store 200-to-400 bracket. It is
still not an exact ceiling or a production SLO; narrower steps, sustained
high-rate soak, real VPS/proxy/storage and future database costs would be
needed for stronger claims. Do not size long-lived operation from the 100/s
fresh-store latency alone.

## Conclusions and remaining boundaries

- Keep the accepted no-payload-backups policy; do not trade away lifecycle,
  deletion work, durability or overload protections for a benchmark score.
- Do not use the fresh-store 200/s step as a long-lived production capacity
  promise: retained metadata changes CPU cost. The full-history follow-up above
  fails the latency threshold already at 50/s.
- No implementation tuning was made to the production application during this
  campaign. Establish comparable before/after runs if optimizing cleanup.
- SQLite/PostgreSQL, WAL cleanup, physical deletion, TLS/proxy, actual VPS
  architecture/storage, distributed workloads, long idle-link populations and
  multi-hour endurance remain outside this executed baseline.
- Compare future SQLite against the same workloads including removal costs;
  this in-memory result does not select database settings or validate its sizing.
